# GitHub Issue Template (Japanese Default)

デフォルト（`--lang` 未指定）はこの日本語テンプレートを使う。`--lang en` のときのみ英語化する。

```markdown
## ゴール
[誰が何に困っていて、この issue で何ができるようになるか。完了した状態を 1〜3 文で]

## 見取り図

~~~mermaid
flowchart LR
  subgraph before
    A1[変更前の構成要素] --> B1[呼び出し先]
  end
  subgraph after
    A2[変更後の構成要素] --> B2[呼び出し先] --> C2[増えた構成要素]
  end
~~~

## なぜ
- [今対応する理由を 2〜4 行で。議論ソース: link or file]

## 受け入れ基準（Acceptance Criteria）
- [ ] AC-1 ...
- [ ] AC-2 ...
- [ ] AC-3 ...

AC 早見表（要旨は上の AC が正）:

| AC | 一言で | 何で確かめるか |
|---|---|---|
| 1 | [AC-1 の要点を一言で] | [テストのファイル名など] |
| 2 | ... | ... |
| 3 | ... | ... |

## 制約・取らないこと
- [守る不変条件・変えてはいけない挙動]
- [スコープ外にするもの（非目標）]
- [AC が今の挙動を置き換えるときは、無くなる・変わる今の挙動を残すか捨てるか]

## 変更対象パス
- <repo 相対パスまたは glob>

## 未解決事項（Open Questions）
- ...

## 完成イメージ
モックは見た目の仕様。HTML の構造・クラス名・CSS は転写せず、既存のコンポーネントで実装する

<details>
<summary>モック</summary>

~~~html
<!-- CSS 込みの HTML モックなど -->
~~~

</details>
```

本文はゴールと境界条件（何を満たせば完了か・何をしてはいけないか）だけを書く。implementer（dev-flow）は
コードを読んで自分で実装計画を立てるので、issue 側の手順は重複し、ずれていれば実装を縛る。

`## 見取り図` は、人間が AC の文章を読み込まなくても変更の形を掴めるようにする図。変更の種類ごとに次の図を書く:

- 構成の変更（ファイル間の呼び出し・構成要素の増減や付け替え）: Mermaid の `flowchart` で `before` / `after` の `subgraph` を並べる
- 処理の流れの変更: Mermaid の `sequenceDiagram`
- データの変更: Mermaid の `erDiagram` か、変更前後の表
- UI の変更: 図ではなく下の `## 完成イメージ`

変更対象パスが 2 つ以上のファイルにまたがり、ファイル間の呼び出し・データの流れ・構成要素が増減または付け替わる変更では必須、
それ以外は節ごと消してよい。図は AC と `## 変更対象パス` に書いた変化だけを描き、AC に無い変化を足さない（食い違いは
`issue-plan-reviewer` が blocking にする）。雛形のフェンスが `~~~` なのは雛形全体が ``` のフェンスの中にあるからで、本文では
` ```mermaid ` でよい（閉じたフェンスの中身は 4000 字に数えない）。見出しは `## 見取り図` のまま使い、`受け入れ`・`受入`・
`完了条件` を含めない（AC 節の判定が変わる）。

AC 早見表は AC の checkbox の直後に、見出しを挟まずに置く（AC 節の中に入るので 4000 字に数えず、ac-lint の判定も変えない）。
AC 1 本につき 1 行で、`一言で` に要点、`何で確かめるか` にテストのファイル名などを書く。早見表は AC の代わりではなく、
要旨は AC が正。行が AC と件数か内容で対応しなければ `issue-plan-reviewer` が blocking にする。

`## 完成イメージ` は任意（見た目を伝える必要が無ければ節ごと消す）。UI の見た目のモックを `<details>` とコードフェンスに
入れ、モックの HTML を実装として転写させないために定型の制約行をそのまま添える。本文の末尾に置く（長いモックより先に
ゴールと境界条件を読ませる）。雛形の例のフェンスが `~~~` なのは雛形全体が ``` のフェンスの中にあるからで、本文では ``` でもよい。

品質基準:
- 各セクションは具体的かつ検証可能に書く。
- 「性能改善」などの曖昧表現は避け、指標/閾値を明記する。
- 専門観点の調査結果（Frontend/Backend/Infra）・実装計画・テスト戦略・リリース/ロールバック・
  悪魔の代弁者のレビュー履歴は節として書かない。そこで分かったことは AC か `## 制約・取らないこと` の 1 行に反映する
  （例: ロールバック手段が要る → 「旧経路を残す」を制約に、テストで守るべき挙動 → AC に）。
- AC 節と閉じたコードフェンスの中身を除いた本文の文章は 4000 字以内。4000 字は本文の文章をゴールと境界条件に絞るための
  上限で、`create_issue.py --kind agent` は超えた本文の起票を拒否する。モック・スキーマ・出力例などの仕様の例はフェンスに
  入れれば言語を問わず数えない。フェンスの外の文章と、閉じていないフェンスの中身は数える。
- コードフェンスに入れるのは仕様の例だけ。調査結果や実装計画の文章を入れない（`create_issue.py` は中身を判定しないので、
  `issue-plan-reviewer` が判定する）。
- AC は repo 内で検証できるものだけを書く。`（人手）`・staging / 本番環境・repo 外の作業を含む AC、repo 内外の作業が
  混ざった AC は dev-flow が人手扱いにして止まるので、`create_issue.py --kind agent` は dev-flow と同じ
  `_lib/ac-actor.mjs` の判定で起票を拒否する。人の作業は下の human issue テンプレートで切り出す。
- agent issue の AC は、コードとテストを読めば確かめられるものか、
  実装を外すと落ちて実装で通るテストファイルを inline code で名指ししたもの（例: 「`_lib/x.test.mjs` が〜を確かめる」）にする。
  実行結果・出力・ログ・計測を観測しないと確かめられないのにテストファイルを名指ししていない AC
  （テストスイートやテストの入口スクリプトの green を含む）は、
  dev-flow が観測型の人手 AC として `ac_human_pending` の HOLD で止める。
  代わりに、テストファイルと確かめる振る舞いを書くか、`human-task` の issue に切り出す。
  テストスイートの green は dev-flow の Validate が gate として確かめるので、AC にしない。
- AC が今の挙動を置き換えるときは、無くなる・変わる今の挙動を残すか捨てるかを AC か `## 制約・取らないこと` に 1 行で書く
  （今の挙動は表示・出力・条件・タイミングのどれでも同じ。書かれていないと implementer が挙動の後退をテストで
  正しい挙動として固めるので、`issue-plan-reviewer` が blocking にする）。

## 変更対象パス

実装 issue（上のテンプレート）は `## 変更対象パス` が必須。書式は 1 行 1 エントリ `- <repo 相対パスまたは glob>`
（SKILL.md の Phase 3「変更対象パス」と同じ）。`/` 始まりのエントリと `..` セグメントを含むエントリは書かない。
`create_issue.py --kind agent` は、欄が無い・エントリ 0 件・`/` 始まり・`..` セグメントのいずれかで起票を拒否する。
計画時点の見積もりであり、後続の並列起動判定はこの欄を「触る範囲の申告」として保守的に扱う。
human issue テンプレートには不要。

## executor（実行者）

各タスクに `executor: agent` か `executor: human` のどちらかを必ず付ける。human マーカーは固定文字列
`executor: human`（SKILL.md の Executor Classification と同じ文字列。言い換えない）。

human 判定基準（いずれかを要するタスクは `executor: human`）:

1. 外部サービスの管理画面操作・アカウント作成
2. secret・API キーの発行と登録
3. DNS・課金・契約
4. 顧客への確認・承認
5. 本番データの手作業操作
6. 実機での手動確認

基準外は `executor: agent`（既定）。executor は SKILL.md Phase 3 の計画上のタスクに付ける。実装 issue
（上のテンプレート）は `executor: agent` のタスクだけを扱い、`executor: human` のタスクは下の human issue
テンプレートで別 issue に切り出し、先に起票する（`create_issue.py --kind agent` は本文に `executor: human` が
残っていると起票を拒否する）。

## human issue テンプレート

`create_issue.py --kind human` で起票する（`human-task` ラベルが付く）。`## 手順` と、checkbox 付きの
`## 完了条件` は必須（無いと起票を拒否する）。

```markdown
## 背景
- 元の議論 / 実装 issue の目的:
- executor: human
- なぜ人手か: [human 判定基準のどれに当たるか]

## 手順
1. ...
2. ...

## 完了条件
- [ ] [完了を人が確認できる観察可能な状態。例: `API_KEY` が repository secret に登録されている]

## 後続 issue
- [この issue の完了を待つ実装 issue。実装 issue 側に `Blocked by #<この issue>` が付く]
```
